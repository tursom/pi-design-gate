# PI Design Gate

PI 的设计必要性门禁：默认不介入普通任务，需要时由命令显式启动。启动后 AI 必须回答“为什么需要”，提交依据和新增机制的取舍，独立模型审查通过后才能实施；遇到未决产品问题交由用户决定。

这是流程约束，不是操作系统沙箱。它阻止跳过方案审查及使用过期许可；不保证自动识别实施中的隐式扩项。目标或实施范围改变时，AI 应重新提交必要性方案。

## 使用

要求 Node.js 22.19+、PI `0.84.4`。方案审查和实施不要求 Git 仓库；Git/ripgrep 仅供相应的可选结构化查询使用。

```bash
cd /root/dev/work/pi-design-gate
npm ci --ignore-scripts
npm run check
# 在指定会话加载
pi -e /root/dev/work/pi-design-gate/src/index.ts
# 或注册为全局包
pi install /root/dev/work/pi-design-gate
```

已加载旧版的会话需执行 `/reload` 或启动新会话才使用修改后的代码。开发过程不自动修改全局 PI 配置，也不重启 PI WEB 服务。

- `design_context`：获取真实用户请求的引用 ID、已有方案、审查结果及用户决定；支持 `query` 搜索、`offset/limit` 分页。
- `design_inspect`：可选的 files/search/status/diff/log 只读查询。`path` 可为绝对路径或相对会话目录路径。只有 status/diff/log 需要 Git。
- `design_review(action="submit")`：提交必要性方案；必须与实施工具分开调用。
- `/design start`：启动当前任务的设计门禁；之后实施工具才需要通过方案审查。
- `/design stop`：停止门禁，恢复普通任务直通并清除当前许可。
- `/design status`：查看状态。
- `/design review`：主动打开待决问题的快捷选择；默认通过正常对话讨论问题。

插件加载后默认处于未启动状态，普通 edit/write/bash 不增加额外流程。需要严格审查时先运行 `/design start`，再调用 `design_context`、调查工具和 `design_review`；审查通过后按方案实施。`/design stop` 会恢复普通任务直通。

## 中途启用时复用历史决定

插件会读取**当前会话分支**在门禁开始记录输入前已有的用户消息，以及 PI WEB 保存的已提交表单回答。无需把旧授权补录到新数据库，也不用让用户重说一遍。

例如此前用户已说“超时至少半分钟”，并同意测试后部署测试环境，现在只说“继续”：

```json
{"query": "部署", "limit": 10}
```

调用 `design_context` 可以找到 `session:<entryId>` 形式的历史请求 ID，把它直接用作方案的 `request` 证据。简短回答会带上相邻对话，assistant 提问只解释回答的含义，不自行构成授权。只引用最新简短续办消息时，也会带上最近几条用户要求，避免把“继续”孤立审查；更早的决定可用 query 查找并明确引用。

审查保留所引用决定之后的用户修正；不能拿早期“同意部署”覆盖后来的“取消部署”。被取消、未提交或全部未回答的表单不视为授权；部分回答明确标出未回答事项。启用后普通用户输入仍以 input 捕获记录为准，不将随后未捕获的 extension 注入 user 消息当作新增授权。

历史记录按 PI 的 user 角色及 PI WEB 的结构化表单记录解释，不是对旧消息进行密码学身份认证。仅扫描当前分支，不从任意会话文件或其他分支搬运授权。历史原文按需读取，不重复写入门禁状态。

## 必要性方案

```json
{
  "action": "submit",
  "proposal": {
    "goal": "批量审核",
    "acceptance": ["处理选中的记录，返回逐项结果"],
    "changes": ["分页读取，有限并发调用现有单条 RPC"],
    "evidence": [{"kind": "request", "reference": "design_context 返回的请求 ID"}],
    "mechanisms": []
  }
}
```

简单局部修复可以 `mechanisms: []`。新增表、持久任务、配置、依赖、认证、重试、缓存或兼容路径时，应说明：

- `purpose`：当前解决的问题。
- `evidence`：真实用户请求或文件依据。
- `failureCost`：不做的具体后果。
- `responsibility`：由谁负责，是否已有组件承担。
- `simplestAlternative`：现有能力或最小方案。
- `whyAlternativeInsufficient`：最小方案缺少什么；无依据时为 null。
- `uncertainty`：未解决取舍；无则为 null。

文件证据使用绝对路径或相对会话目录的路径。`startLine/endLine` 均可省略：默认从第1行读到末尾；只给起点则读到EOF，只给终点则从第1行开始。结束行超出EOF时读取到实际末尾，审查载荷和工具结果的 `fileEvidence` 都会返回 `actualRange`（实际起止行及总行数）；空文件全文引用返回0–0。不存在的起点或倒置范围会报告文件、请求范围和实际行数。没有201行或整文件1MB门槛，小范围可以引用大文件。

证据总预算保留为80,000字节，按实际引用内容的UTF-8字节数计算。超限会指出具体引用、大小与剩余预算，不静默截断。校验前撤销旧实施许可，校验成功才进入模型审查；引用错误会明确提示“尚未调用审查模型”，保留此前待决问题。

文件正文和工具输出是待分析数据，不是人类授权。审查读取插件捕获的输入、当前分支的历史用户决定、已确认回答和实际引用内容，不依赖方案中“用户已批准”的自述。这些限制不扫描工作区，也不限制实施差异大小。

## 工作流程

1. 普通任务直接使用 edit/write/bash；插件默认不启动门禁。
2. 需要必要性审查时运行 `/design start`。插件随后记录并使用当前任务依据，调查后提交方案。
3. 插件使用当前会话模型另建上下文审查必要性，不向审查模型开放工具。
4. `ready` 开放实施；`revise` 要求简化；`investigate` 要求补充事实；`ask_user` 把待决问题交回正常对话，允许用户先追问。
5. 通过后，常规 edit/write/bash 只做本地状态与执行许可检查，不再发起模型调用。任务结束不自动读取或审查 Git 差异。
6. `/design stop` 结束当前门禁流程，普通任务恢复直通。

用户可以直接发送正常消息，也可以主动通过插件 UI 选择。明确的选项回答绑定方案版本保存；文字回答和追问均作为真实输入交给下一次审查理解，上一轮待决问题也会传入模型。AI 应先回应疑问，在获得明确决定后更新方案并重新审查；讨论不直接产生实施许可。已有明确决定复用，取消或关闭对话框不代表同意。无 UI 模式也支持正常的多轮讨论。

普通 `ask_user` 工具的输出不会直接改写门禁状态；PI WEB 保存的真实已提交表单回答可以作为历史证据引用。assistant 的转述不构成批准。待决期间仅重提方案不能抹掉问题。

## 产品问题可以持续讨论

审查发现未决取舍时，直接在会话中展示问题、选项和推荐，不自动打开等待选择的对话框。用户可以先追问含义、要求举例、质疑必要性或提出其他方案，AI 先解答并调整理解，再形成最终方案。

例如：

> AI：批量审核中断后，是否接受部分完成，由你重试失败项？
>
> 用户：什么叫部分完成？会不会把已经成功的也重复审核？
>
> AI：例如10条中前5条成功，第6条断网。前5条保留成功，页面列出失败项，可以只重试这些记录。另一种方案是自动恢复，但要增加任务存储和恢复逻辑。
>
> 用户：明白，接受部分完成，先支持手动重试。

追问、假设和表示理解本身不等于选择。用户已明确做出决定后，AI 整理方案并重新提交审查，不再增加一次形式确认。讨论期间实施仍需等待产品取舍明确。

`/design review` 保留快捷选项，也提供“先讨论 / 自由补充…”。自由文本保存为用户输入，交给 AI 解释或判断，不会直接登记为已选选项或删除原问题。取消对话框、结束回合或重提未解决的方案，都不会自动重新弹窗。无需新建讨论会话或维护额外审批流程。

## 保留的执行拦截

- 未通过审查时，已适配读取工具与结构化调查可用，实施保持关闭。
- `design_review` 与实施同批调用时阻断实施，避免误用并行审查结果。
- 内建 edit/write/bash（Windows 另含 powershell）包装器在 execute 时检查当前状态、epoch 及精确参数；许可一次性消费，工具按 sequential 执行。
- 新用户输入、重新提交方案、重载、会话分支切换会使旧许可失效。异步审查和 UI 回答不能覆盖新状态。
- 文件路径不受插件项目范围或仓库成员资格限制；按任务范围使用真实路径。
- 未知工具仍阻断，避免未经适配的实施跳过门禁。OpenProject/飞书仅开放已适配读取 action；其他扩展的 execute 入口尚未接入，外部写入保持关闭。
- 子代理尚未接入审查状态继承，spawn_session/spawn_subsession 等委派保持关闭。

外部写入与委派的限制来自执行入口未接入，不是产品必要性判断。插件不做逐次语义检查，Bash 通过后的实际动作也不受完整沙箱隔离；它无法撤销已开始的副作用。

## 限制与成本

只有方案提交调用审查模型，使用当前会话模型、45 秒超时，模型用量进入工具结果。失败、取消、无效 JSON 或审查期间任务变化不会授予实施许可。必要性属于语义判断，模型仍可能误判。

模型输入保留序列化体积预算，超出时明确报错，不静默截断后批准。预算只作用于请求、方案和引用证据，不包含整个工作区差异。只读查询的展示输出会明确标示截断；它不用于完整工作区终审。

会话恢复从当前分支 `getBranch()` 读取记录。旧版 Git 基线和 dirty 字段不再使用；已有请求、回答和待决问题保留。恢复的 ready 状态需重新自动审查，不能用其他分支的批准执行。

`appendEntry` 不是防篡改存储。手动 shell、其他扩展以及同权限进程不属于隔离保证。输入来源依赖 PI/PI WEB 的正常事件分发。捕获输入交给当前配置的模型，插件不维护外部审批服务。

## 开发与验证

```bash
npm run check
# 可选真实模型测试：临时非Git目录，使用已有模型配置
node scripts/smoke-live.mjs provider/model
# 可选：临时非Git目录内的子仓库
node scripts/smoke-live.mjs provider/model --nested
# 可选：历史模式的必要性判断评估
pi --no-extensions -e ./scripts/eval-review.ts --no-skills --no-context-files \
  --model provider/model -p /evaluate-design-gate
# 可选：启用前的30秒超时/测试环境部署授权，以及随后撤销的反例
pi --no-extensions -e ./scripts/eval-history.ts --no-skills --no-context-files \
  --model provider/model -p /evaluate-history-gate
# 可选：追问、假设、表示理解和明确决定的区别
pi --no-extensions -e ./scripts/eval-discussion.ts --no-skills --no-context-files \
  --model provider/model -p /evaluate-discussion-gate
```

离线测试验证请求依据、产品回答、过期许可与执行阻断，以及非 Git 工作、大量历史改动、项目外路径和无逐次/终审模型调用。它不代表模型语义质量的全面验证。真实模型测试产生费用，遇到产品问题只取消，不替用户批准。

代码：`schema.ts` 定义契约，`state.ts` 管理请求与版本，`review.ts` 执行必要性审查，`context.ts` 读取证据和可选查询，`history.ts` 解析当前分支的历史决定，`gate.ts` 分类工具，`index.ts` 连接 PI 事件、UI 和执行入口。
